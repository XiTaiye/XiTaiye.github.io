知识库文档上传与分段：六种分段方式的技术路线

发表于2026-05-03|更新于2026-11-26|Java
|阅读量:

拆解「上传一个文件 → 变成可召回的向量」这条链路的完整实现：两段式异步流水线、按扩展名分发的解析器、六种分段策略（前端可选五种）、分段与向量化的衔接、以及五张表与两条状态机。
全部结论来自代码与本机库的实测数据，未实现的能力在文末单列，避免按想象中的 small-to-big 去翻代码。

一、结论先行

事实 说明
后端枚举 6 种分段方式 SegmentType.java:43-68：fixed_length / paragraph / structured / symbol / semantic / llm_semantic
前端可选 5 种 const/knowledge.ts:45-76 硬编码 5 项；structured 不在选项里
structured 是强制项 文件扩展名为 csv/tsv/xls/xlsx/json 时服务端直接接管，UI 禁选（KnowledgeTool.java:402-413、:421-429）
默认策略是 semantic SegmentProperties.java:44，segmentLength 默认 800
没有 overlap / 父子块 / rerank / OCR 见第十节「未实现清单」，这是读代码时最容易找错方向的四项
上传与摄取是两个接口 /upload 只落 OSS + 文档记录；解析分段向量化由 /ingest-task/start 异步驱动

二、全链路：两段式异步流水线

关键设计是上传与摄取解耦：

  • 没有消息队列，靠 CompletableFuture + ThreadPoolTaskExecutor。线程池参数：核心 = CPU 数、最大 = 2×CPU、队列 200、拒绝策略 CallerRunsPolicy（背压回落到调用线程）、线程名前缀 kb-ingest-、优雅关闭等待 60s（KnowledgeExecutorConfiguration.java:67-85）。
  • 任务记录在调用线程创建而非异步线程内，注释写明理由：返回的主键要能立刻用于查询进度（AiKnowledgeIngestServiceImpl.java:78）。
  • 重新摄取时先 clearByDocument(documentId) 清掉旧分段及其向量；但分段失败时提前 return，原有内容保留（:99 与 :91-95 的顺序关系）。

三、上传阶段：走的是 S3 兼容对象存储

AiKnowledgeDocumentServiceImpl.java:80 注入的是 OssTemplate，:219/:223 调 ossTemplate.putFile(...)——既不是阿里云 OSS 也不是 FastDFS，而是配置驱动的 S3 兼容实现（本机跑的是 rustfs）。

上传进度有两套通道，别混淆：

  1. 后端通道：传 uploadId 时用 ProgressTrackingMultipartFile 包装输入流，进度写 Redis，键前缀 upload:progress:，30 分钟过期（ProgressUploadTracker.java:53,80-110）。
  2. 前端通道：知识库上传页用的是 axios 原生 onUploadProgress，**并没有传 uploadId**（api/knowledge/document.ts:31-47）——uploadId 与 source 参数在该页面属未使用状态。

文档表 ai_knowledge_document 只有 name/url/type/size/source/file_time，没有摄取状态列；状态全挂在两张任务表上。上传后反复预览走 Redis 30 分钟缓存（AiKnowledgeDocumentServiceImpl.java:74-78,162-194）。

四、解析阶段：按扩展名分发，图片回插正文

KnowledgeFileServiceImpl.java:86-144 按扩展名从 FileHandlerFactory（:99-115）取处理器，没有对应处理器直接抛异常（:104-107），通过 URL 打开流读取。

格式 解析库 证据
pdf Apache PDFBox PdfFileHandler.java:30-41，支持型 :84
doc / docx POI XWPF / HWPF WordFileHandler.java:31-47，:90
xls / xlsx POI WorkbookFactory ExcelFileHandler.java:29-35，:68
csv / tsv 自定义行编码 CsvFileHandler.java:62
ppt / pptx POI HSLF / XSLF PptFileHandler.java:30-50，:86
md / txt / log / html / json / xml / svg / yaml / java / sql 各自 handler 见 handler/impl/ 目录

图片处理：PDF/Word/PPT 的内嵌图片经 KnowledgeImageUploader（:53-137）上传对象存储，并以 Markdown ![]() 标签插回正文，调用点 PdfFileHandler.java:629、WordFileHandler.java:413,1259、PptFileHandler.java:334。

扫描版 PDF 会直接失败：报错「该PDF疑似扫描件…请提供文本版PDF或启用OCR」（PdfFileHandler.java:436）——OCR 只有提示，没有实现。

五、策略分发：三级优先级

KnowledgeTool.getSegmentType(assetType, properties, segmentTypeCode)（:402-413）：

也就是说：用户在界面选的分段方式，对 csv/xlsx/json 完全无效。前端也据此在结构化文档时禁选策略按钮（ingest-settings.vue:13）。

策略实例由 FileSegmentFactory.java:75-92 产出，统一契约 FileSegment.segment(SegmentRequest) → List<String>（FileSegment.java:36-52）。SegmentRequest 只有 5 个字段：content / segmentType / segmentLength / segmentSymbol / segment（:42-68）——没有 overlap、没有父块 ID。

六、五种可选策略逐个拆解

1. semantic 语义分段（默认）

在段落分段的基类之上追加两条边界（SemanticSegment.java）：

  • Markdown 标题 ^(#{1,6})\s+（:52,100-103）
  • 中文主题转换词表——「然而 / 此外 / 综上所述」等（:57-60,106-111）
  • 图片密度阈值 3/10/5（:65-75,114-118）：图片密集的段落强制保持可切分，零星图片跨段时才走连续性保护

适用：结构清晰的文档。

2. paragraph 段落分段

完全继承基类（ParagraphSegment.java:59-68 + AbstractParagraphSegment.java:50-70,122-219,241-268）：

  1. 按空行 \n{2,} 切段；
  2. 累积到 segmentLength，允许溢出 MAX_OVERFLOW_CHARS=100；
  3. 超长段落先按句子边界二次切分为子块（splitLongParagraph），再走累积逻辑。

标题续段机制（:156-167、:200-204）：识别到标题后记为 currentTitle，其后每个新分段自动带上该标题前缀（若该段自身已含标题则不重复）。这解释了向量库里的实测现象——text 字段常以 ### 4.3.36 编辑独享桌面资源 … 这样的标题开头。

文档元信息只留首段（:147-154 + isDocumentMetadata() :276-286）：「Word文档信息 / 作者 / 页数」这类块不重复进每个分段。

3. fixed_length 固定长度

按 segmentLength 字符滑窗切，但会回溯到最近的句/段边界（. 。? ? ! ! \n）断开，且回溯不超过半段长（FixedLengthSegment.java:75-139）；isInsideImageTag（:148-166）保证 Markdown 图片标签不被从中间切断。无 overlap。

适用：没有明显结构的长文本。风险最高的一项：没有标题续段机制，可能把 ## 3.2 这类标题切成半截。

4. symbol 符号分段

按用户传入的分隔符 content.split(Pattern.quote(symbol))（默认符号 "$$"，SegmentConstant.java:43）整块取出，再按长度装箱；单块超过 2×segmentLength 时强制按句边界拆（SymbolSegment.java:151-202,211-240）。**分隔符为空或异常时回退 SemanticSegment**（:59-61,107-111,123-126）。

适用：每条内容以固定符号隔开的文本（如导出日志、拼接语料）。边界完全由数据作者控制。

5. llm_semantic 大模型语义

让大模型判断主题边界（LLMSemanticSegment.java）：

  • prompt 要求每段 ≤ segmentLength 字符并输出 [SEGMENT n] 标记（:316-329）
  • 按 \[SEGMENT\s*(\d+)\] 解析回填（:66,337-360）
  • 内容超过 inputLength=20000 或 LLM 未启用 → 回退 semantic（:99-105）
  • 超长内容按 modelMaxChunkSize=4000 分块逐块调模型（:157-186）
  • **任何失败都回退 semantic**（:130-133）

代价最高：耗时与费用都上去了，且引入了「模型输出格式不合规」这一类新失败模式。

6. structured 结构化（不可选，自动生效）

根本不走文本切分：CSV/Excel/JSON 的 handler 已经把每行编码成 {index, content} 两个键（KnowledgeConstant.java:38-40；生成点 CsvFileHandler.java:408-409,424-425、ExcelFileHandler.java:216-217,231-232、JsonFileHandler.java:180-181），StructuredSegment.java:73-108 把一行记录变成一个分段，无长度参数。

九、分段 → 向量化：双文本列是关键

ai_knowledge_segment 有两组文本列，职责完全不同（AiKnowledgeSegmentServiceImpl.batchSave():168-204）：

列 写入时机 用途
index_text / index_length 所有文档都写 参与 embedding 的文本
content / content_length 仅结构化文档写 命中后回补的完整内容

非结构化文档只写 index_text，content 留空——本机库 684 段 content 全为 NULL 正是这个分支的结果，不是丢数据。

向量化流程（AiKnowledgeVectorizationServiceImpl.java）：

  • metadata 四个键：knowledgeId / documentId / segmentId / fileName（MetaDataConstant.java:41-49）。实测 Milvus 里就是 {"knowledgeId":"…","fileName":"….pdf","documentId":"…","segmentId":"…"}。没有原文偏移量。
  • 向量主键 ↔ 分段：入库返回的 UUID 逐段回写 embedding_id，即 Milvus 的 id 字段。
  • 维度：优先取 ai_model.dimension，为空才按供应商默认（OpenAI 1536 / Qwen 1024 / Zhipu 2048 / Ollama 768 等，RagConstant.java:65-73；使用点 RagFactory.java:57,82-93）。向量库连接测试会先校验模型维度与库维度一致（RagEngineServiceImpl.java:316-319）。
  • 供应商分发：embedding 模型 9 家、向量库 8 种（redis/milvus/pgvector/qdrant/elasticsearch/opensearch/chroma/oceanbase，RagConstant.java:53-60）。Milvus 建集合用 ai_vector_store.collection + dimension，索引 COSINE + AUTOINDEX（MilvusEmbeddingStoreTemplate.java:56-63）。
  • 手工编辑单条分段走逐条异步 asyncUpdateVector()（:455-504）。

十、召回侧：有 topK/阈值与多库并行，没有 rerank

  • 参数：maxResults=5、minSimilarity=0.7（RagConstant.java:78-83）；应用层检索节点可配（RetrievalConfig.java:44、ChatbotRetriever.java:66）；界面命中测试给了 1-10 与 0-1 滑块（recall.vue:24-43,104-105,126-127）。相似度过滤在向量库查询内完成（RagSearchServiceImpl.java:164）。
  • 多知识库并行检索：固定 10 线程池（RagSearchServiceImpl.java:72,104-130）。
  • 防跨库命中：检索按 knowledgeId metadata 过滤（RagEngineServiceImpl.java:290-291）。
  • 最接近 small-to-big 的机制：命中后按 segmentId 取分段，把 content 填成 auxText（RagKnowledgeServiceImpl.java:199-236），拼 prompt 时输出「主要说明 + 补充说明 + 来源」（:110-125）。但它只对结构化文档生效——非结构化文档 content 为空，等于没有回补。

十一、状态机与实测数据

三条状态线（TaskStage.java:32-45、KnowledgeConstant.java:50-54、RagConstant.java:102）：

本机库实测（2026-11-26）：

指标 值
实际用过的分段类型 semantic 773 段（均长 665）、llm_semantic 12 段（均长 428）
分段总数 684 条（当前存活文档），content 全为 NULL
Milvus blade_ai 584 条，字段 id VarChar(36) / text VarChar(65535) / metadata JSON / vector FloatVector dim=1024，COSINE
vector_state done 583 / error 101

排障线索：vector_state=error 且 vector_attempts 打满时，优先查向量模型的地址与密钥是否匹配——provider 是「端点 + 密钥」的维护单位，而供应商面板保存会把同组所有模型的 base_url 刷成同一个值（批量 update，且 locked 字段在该路径上未被检查）。把 embedding 模型放到独立 provider 分组、指向真正支持向量的端点，是这类失败的直接解法。分段本身是成功的，失败只发生在 embedding 调用，所以「分段数对得上但召回为空」通常就是这个原因。

十三、选型建议

文档形态 建议策略 理由
带清晰标题层级的规范文档 semantic（默认） 标题 + 主题转换词双重边界，标题续段自带上下文
结构松散但段落分明 paragraph 只看空行，行为可预测
无明显结构的长文（聊天记录、口述稿） fixed_length 等长 + 句边界回溯，注意标题可能被切断
作者已用固定符号分条 symbol 边界由数据作者决定，最可控
语料质量要求高、预算充足 llm_semantic 语义最贴，但慢且贵，失败静默回退 semantic
csv / xlsx / json 无需选 structured 强制生效，一行一段

一句话总结这条链路的设计取向：用「任务表 + 状态机 + 批处理」把不可靠的外部依赖（文件解析、embedding 调用）拆成可重试的两段，分段策略则统一收敛到 List<String> 这一个契约上，新增策略只需实现 FileSegment 并注册进工厂，不影响下游向量化。
