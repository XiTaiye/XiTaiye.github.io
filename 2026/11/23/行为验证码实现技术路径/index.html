行为验证码实现技术路径：五种题型的出题、渲染、校验与票据核销

发表于2026-11-23|更新于2026-11-26|Java
|阅读量:

以登录页弹出的「安全验证」为入口，拆解五种题型从出题、渲染、作答、校验到登录票据核销的完整链路。
涉及工程：web（前端）、project-Tool / project-core-oauth2（框架底座）、project-api 与 project-AI-Cloud-Pro（业务侧接入）。

一、能力全景

行为验证码不是「一张静态图 + 一个字符串」，而是一套完整的出题—作答—核销协议：

层 位置 职责
题面生成 project-Tool/project-core-auth/project-core-oauth2/.../behavior/ Java2D 纯代码绘制底图与题面，产出 base64 图片 + 答案坐标
出题/校验端点 OAuth2TokenEndPoint（SPA）/ OAuth2AuthorizationEndpoint（SSO 登录页） GET /oauth/behavior、POST /oauth/behavior/check
生命周期存储 OAuth2BehaviorHandler Redis 存题目（5 min）与一次性票据（3 min），取后即删
登录核销 业务侧 BehaviorTokenGranter behavior 授权模式，先核销票据再走密码认证
交互呈现 web/src/components/behavior-captcha/ 弹窗状态机 + 四个作答面板 + 坐标换算

五种题型由 BehaviorFactory 等概率随机选取（BehaviorFactory.java:46）：

type 题型 交互 答案形态 容差
word 文字点选 按明文提示依次点字 x,y;x,y;x,y 28 px
idiom 成语语序点选 不下发提示，自行识别成语并按语序点 同上 28 px
puzzle 滑块拼图 横向拖滑块对齐缺口 单值 x 8 px
concat 拼接还原 拖滑块使上下纹理错位复位 单值位移量 8 px（取环绕差）
rotate 旋转还原 拖滑块转动内圆对齐外围 单值角度 8°（取圆周差）

二、题面渲染：全部由代码生成，零图片资源

2.1 底图 = 主题 × 构图风格

AbstractBehaviorGenerator 维护 10 套同色系主题（深海蓝、暮紫、松石绿、琥珀棕……每套 7 个色槽：渐变起/止、光斑 A/B、流线 A/B/C），以及 5 种构图风格：FLOW（贝塞尔流线）、WAVE（正弦波纹束）、GEOMETRIC（低多边形三角拼接）、GLOW_DOTS（光点星轨）、GRID（斜向细网格）。

出题时随机组合「主题 × 风格」，再叠加渐变、3~5 个柔光斑和每 600 px² 一个的极细噪点。噪点密度与透明度都刻意克制，只为抬高机器识别成本而不显脏。

风格不是随便选的：依赖纹理连续性做对齐线索的题型会限定风格池——concat 排除无方向感的光点风格（ConcatBehaviorGenerator.java:72），rotate 只允许具备贯穿性线条的 FLOW/WAVE/GRID。

2.2 2× 超采样与统一坐标契约

所有图片按逻辑尺寸的 RENDER_SCALE = 2 倍物理像素渲染（680×440 显示为 340×220），保证高 DPI 屏清晰；画笔统一 scale(2,2)，绘制代码始终用逻辑坐标。

关键约定：接口下发的 width/height 与答案坐标全部是逻辑坐标，渲染倍率对前端完全透明。前端拿到的 stageSize、坐标换算基准都来自服务端下发值，而不是前后端各存一份常量（word-panel.vue:81）。

2.3 出口编码

  • 无透明通道题面 → JPEG DataURI，质量 0.9（再低渐变会出色带）
  • 拼图块 / 旋转内圆 → PNG DataURI（需 alpha）

三、文字点选（word）：Java2D 画字

WordBehaviorGenerator.renderWordPuzzle() 是文字类题型的公共引擎（WordBehaviorGenerator.java:145）：

  1. 3×2 网格布字：6 个字符分配到打乱后的网格单元，单元内随机抖动，margin = 最大字号/2 + 4，从根上保证字符互不重叠、点击不歧义。
  2. 前 targetCount 个即答案：字符列表的前 N 个按序就是目标，其中心点串成 x,y;x,y 存 Redis。
  3. 伪装绘制（drawCamouflagedChar）：
    • 颜色取主题流线同系色，alpha 随机 90~150，再补一层 alpha 60 的暗色伪轮廓 → 字符与底图「融合」而非高对比浮出；
    • 字体每字随机（混排字体使字形特征碎片化）、字号 34~44 随机、旋转 ±35°、错切 ±0.18。
  4. 覆盖层：字符层之上回叠 2 个柔光斑压低整体对比，再画 3 条同系色弧线切断字符轮廓 → 形成「若隐若现」的观感。

实际题面（橄榄绿主题 × 几何风格，提示串 革/寿/月，目标数 3）：

图中六个字「寿 原 夏 革 亭 月」按 3×2 网格散布，各自随机字体、字号、旋转与错切；字符色与底图同系，靠 alpha 90~150 融合而非高对比浮出。作答需依次命中「革 → 寿 → 月」三字中心，容差 28 px。

字体探测与降级

启动时探测一次字体池（resolveTextFonts，优先 PingFang SC / 微软雅黑 / SimHei 等），并据此得到 CJK_AVAILABLE：

  • 中文字体不可用 → word 降级为字母数字点选（无歧义 ASCII 字符池）；
  • idiom 直接复用父类 generate()，即整题退化为明文提示点选（IdiomBehaviorGenerator.java:90）。

这条降级链是 Linux 容器（缺中文字体）部署时最容易踩的坑：现象是「图上的汉字变成了方框/字母」。

四、成语语序点选（idiom）：对抗强度最高的一型

设计要点（IdiomBehaviorGenerator.java:34）：

  • 内置约 200 条四字成语词表，收录时保证条目内四字互异，避免同图出现重复字导致作答歧义；
  • 取一条成语的 4 个字 + 2 个干扰字（干扰字用 pickDistinctChars 排除与成语重复的字），共 6 字乱序布入 3×2 网格；
  • renderWordPuzzle(drawChars, 4, false) —— 第三个参数 withPrompt = false，即接口不下发 prompt 字段；
  • 校验逻辑、坐标契约、容差完全复用 word。

安全价值：OCR 即使识别出全部字符，仍需具备成语知识才能确定「哪 4 个字 + 什么顺序」，把攻击门槛从「视觉识别」抬到「语义理解」。

前端配套：word-panel 的提示条在 prompt 缺省时降级为序号进度（chips 计算属性 + is-ordinal 样式，word-panel.vue:87），也就是截图里底部那排 1 2 3 4。所以「图中没有提示文字」是设计如此，不是 bug。

实际题面（暮紫主题 × 流线风格，接口只下发 targetCount=4，无 prompt）：

六个字「万 巷 人 丝 河 空」乱序铺开，正确答案是成语「万人空巷」的语序点法：万 → 人 → 空 → 巷；「丝」「河」为干扰字。作答满 4 个后前端才提交，提示条用 1 2 3 4 序号反映进度而非目标字符。

两型提示条的差异只在服务端有没有下发 prompt，前端据此在「字符 chip」与「序号 chip」之间切换。左：word 下发 prompt=["琴","波","中"]；右：idiom 无 prompt、仅 targetCount=4。

五、滑块类三型

puzzle（滑块拼图）

  • 缺口限制在画布右半区（gapX ∈ [W/2, W-70]），避免起始位置即命中；
  • 形状 = 圆角矩形 + 顶部凸起圆 + 右侧凹口（Area 布尔运算）；
  • 先按缺口位置从底图 setClip + drawImage 抠出带 alpha 的拼图块（PNG），再在底图缺口上叠暗色遮罩 + 外亮内暗双描边制造凹陷感；
  • 只下发 pieceY，用户仅能横向拖 → 答案退化为单值 gapX，容差 8 px；
  • 前端滑轨行程与拼图块行程等比映射：pieceX = progress * (width - pieceSize)（puzzle-panel.vue:76）。

concat（拼接还原）

底图沿随机高度水平切分，下条整体循环左移 offset，用户右移复位。因位移在画布宽度上是循环的，校验按环绕就近差取：delta = |moved - target| % WIDTH，再判 min(delta, WIDTH - delta) <= 8。

实现细节值得记一笔：像素搬移直接在物理像素域做（两段 drawImage 源/目标矩形完成循环位移），刻意绕开缩放画笔，避免逻辑目标区与物理源区两套坐标混用出错。

rotate（旋转还原）

从画布中心截圆并预旋转 45~315°，外围保持原状；答案 = 360 - 预旋转角（互补角），校验按圆周取就近差。内圆描边 alpha 90 用于柔化拼接边缘。

六、作答与校验协议

三个防滥用设计：

  1. 一次性题目：答案先取后删，同一 key 只允许校验一次，失败即换题，穷举无意义；
  2. 一次性票据：票据同样 getAndDel，验证通过后 3 分钟内只能登录一次；
  3. 模式以服务端留存为准：校验分发用 Redis 里的 type，客户端伪造 type 无效。

七、前端接入

组件结构

状态机与体验细节

loading → ready → checking → success | fail：

  • 图片预解码：base64 题面在响应到达时尚未完成首帧绘制，直接切视图会让舞台闪空白。preloadImages() 用 Image.decode() 等解码完成再切，骨架屏覆盖整个等待期（index.vue:212）；
  • 作答满 targetCount 后延时 300 ms 提交，让最后一个序号标记完成入场动画；
  • 校验失败展示抖动反馈，900 ms 后自动换题（题目已被服务端消费，不换题无法重试）；
  • 校验成功延时 700 ms 关闭弹窗并 emit('success', {key, ticket})。

八、部署与排查清单

现象 根因 处理
汉字渲染为方框 / 整题变字母点选 容器缺中文字体，CJK_AVAILABLE=false 触发降级 镜像内安装 fonts-noto-cjk，或挂载字体目录
字符看不清、像「没显示」 伪装色 alpha 90~150 + 覆盖光斑 + 干扰线的融合设计，叠加 JPEG 0.9 压缩 属预期观感；如需降低难度，调 drawCamouflagedChar 的 alpha 区间或减少 drawVeilGlows 层数
点击总是判失败 前端坐标未按逻辑尺寸换算 / 前后端常量不同步 坐标一律用服务端下发的 width/height，勿写死 340×220
校验通过但登录仍报验证失败 票据被重复消费或超过 3 min TTL 检查 Captcha-Key/Captcha-Code 头是否原样带回
想抓题面图排查 — captcha-assets/grab.mjs 循环拉取五种题型并落盘 base64 图（见第十节）

实测补充：本机（Windows，微软雅黑可用）抓取的五张题面中，word 与 idiom 的汉字均正常渲染，无方框与缺字。因此「汉字有时不显示」在本环境不是字体降级问题，而是伪装色融合 + 光斑覆盖导致的视觉不可辨；若线上出现真正的字符缺失，先按第一行确认容器字体。

九、可复用的设计思路

  1. 答案即坐标，校验即距离：把「识别结果」降维成坐标串比对，服务端无需存任何图像特征，校验成本 O(n)。
  2. 语义层加固视觉层：idiom 用「不下发提示」这一行参数差异，就把题型从视觉任务升级为语义任务，成本极低、收益明显。
  3. 风格池按题型约束：对齐类题型限定纹理风格，避免生成「理论上无法完成」的题目——这是自动出题系统容易漏掉的正确性约束。
  4. 坐标契约单向下发：尺寸、目标数、提示全部由服务端下发，前端不复制常量，杜绝前后端漂移。
  5. 取后即删 + 票据两段式：把「人机验证」与「身份认证」解耦成两个短 TTL 的一次性凭证，既防重放又限制爆破。

十、配图与复现

题面图（纯 base64 图片本体）由 captcha-assets/grab.mjs 从本机运行中的 project-api 抓取：循环请求 GET /project-auth/oauth/behavior，直到五种题型各取一张，base64 解码落盘至 captcha-assets/images/。

弹窗图（含标题栏、题面、提示条/滑轨的真实渲染）由 captcha-assets/shot.mjs 用无头 Chrome 走真实登录流程采集：打开前端登录页 → 填表单 → 点登录触发弹窗 → 等题面图解码完成 → 按副标题识别题型 → 只截验证面板这个元素。题型是随机的，脚本会自动点「换一题」直到集齐目标类型，账号密码仅作命令行参数传入、不落文件。

因是随机出题，每次运行得到的主题、风格、成语与坐标都不同；grab.mjs 会打印每道的 type、key 与元信息（targetCount、prompt、pieceY、sliceY、ringSize），可直接对照图中观感验证参数契约。

注意：project-dev/captcha-verify/grab.ps1 是同类脚本，但开头会清空目录内所有 *.jpg/*.png，该目录还留有历史抓取图与 OSS 相关 SQL，复现时建议用本节的 captcha-assets/。
